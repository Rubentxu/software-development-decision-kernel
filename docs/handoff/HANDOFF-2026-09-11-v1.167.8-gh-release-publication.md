## Lessons (carry into next release script rewrite)

1. **`scripts/install.sh` has a hard contract on the unified tarball
   layout.** The `detect_asset` function is the source of truth for the
   asset name (it builds `sddk-${os}-${arch}-musl` on Linux), and the
   unified tarball MUST be named `sddk-${VERSION}-${ASSET}.tar.gz`. The
   tarball MUST extract to `bin/sddk` + `framework/`, no nesting. The
   `sddk dev install --source` parser expects `[bundle]` + `[contents]`
   in BUNDLE.toml (v2 nested schema, not the flat one we hand-wrote in
   M7.9). These are **three silent contracts** — none of them fail
   loudly when the publish is wrong; they fail when a downstream
   install runs. A `bash scripts/release.sh --dry-run` followed by a
   per-attempt install from CDN (the exact loop used here) is the
   only safe way to converge.

2. **The `scripts/release.sh` canonical script was NOT used.** It would
   have caught all three issues (it generates the correct layout via
   its own pipeline), but we already had `dist/` artifacts from the
   M7.9 cycle. A future hygiene cycle should either:
   - Make `release.sh` idempotent and re-runnable (today it does a
     full build + test, which is what blocked us from using it
     after-the-fact), or
   - Document the manual fallback path that converges on the install.sh
     contract (the four-attempt loop above) as an explicit recipe in
     `docs/RELEASING.md` § "Manual fallback".

3. **CDN caching adds 1–4 minutes of latency per re-upload.** The
   `gh release upload --clobber` updates GH storage immediately but
   the public CDN may serve the old asset for ~5 minutes (cycle-47
   D4 baseline). The poll-loop in this handoff (`curl | sha256sum`
   against the expected SHA) is the only reliable freshness check —
   `gh release view` reports the latest metadata but does not check
   CDN freshness.
